# 独立画面观察上游故障与恢复

排查对象为 `record-4kibh7`，第 1 轮的 `sanguo-media-observe`。原始执行快照及验证数据保存在 `logs/observation-repair-2026-09-08/`。

## 原因

第 0 帧实际使用有效的本地 JPEG、GPT-5.6 Sol、Messages 协议、`stream=false` 和串行映射。三次上游请求分别返回 HTTP 503、524、503，耗时分别为 122898、126173、123803 毫秒。上游明确返回“模型过载”，三次预算耗尽后节点停止，总耗时 377529 毫秒。

这次失败没有产出观察报告，图片加载及 JSON 参数内的帧地址替换正常。适配器已经有限重试，不能通过在映射或浏览器层再套重试来解决持续的上游容量不足。

完全相同的第 0 帧请求随后经 `/api/node-run` 重放，单次返回 HTTP 200、完整 JSON，耗时约 125 秒。没有修改模型、返回方式、提示词、图片或并发配置。

## 恢复逻辑修复

原先 `manualRetryRuns` 对所有手动重试都增加 revision。映射节点中途失败时，即使其他帧已有成功流水，再次执行也会更换所有帧的请求标识，无法命中服务端成功缓存。

现在仅对因明确传输错误失败的映射文本节点保留 attempt/revision 及当前复核输入。持久缓存仍同时验证请求指纹与实际图像内容，复用已有成功帧，失败和未开始的帧正常调用。修改输入、模型、提示词或图片会使持久缓存失效；主动重跑成功节点及报告质量失败仍使用新身份。下游照常失效，原执行记录保持不变。

分支恢复还保留原 `routeInputContext`，避免遗漏分支 `contextPatch` 中的修正指令或补采计划。上下文重建仍用当前成功前序节点的输出覆盖旧快照。

没有增加自动重试次数或更换审核模型。上游仍可能过载；此次代码修复保证恢复时能保留已完成的工作，不能保证外部模型永不报错。
