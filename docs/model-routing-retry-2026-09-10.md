## 本次结论

最新失败记录为 `record-u31is8`，创建于北京时间 2026-09-10 13:37:25，继承请求 scope `record-kytilm`。失败节点是“本集场景大纲”，不是昨日 `record-d2l7fp` 的“场景短分镜”。

revision 1 实际产生了两个成功文本响应。第一次生成先收到 11 次 `503 / model_not_found / No available channel`，第 12 次请求恢复，整个调用耗时 541908ms；第二次生成直接成功，耗时 137613ms。第三次内容修复调用收到 1 次 RPM 限流、19 次无可用通道，20 次传输尝试共耗时 2360098ms（约 39.3 分钟），没有返回第三份完整候选。

因此，这里的“20 次”是同一个内容生成请求内部的供应商传输重试，并非模型提交了 20 版大纲而均未通过。此前 revision 0 还有明确的 403：上游报告所路由的 Sonnet 模型需要 PRO 权限、可用凭据均为 FREE。仅凭该报错不能断言是谁更改了模型映射。

代码根因是只按 HTTP 状态判断：全部 503 都进入同一个 20 次重试循环，错误正文中的通道、权限和额度原因没有参与决策；每次请求可单独等待很久，又没有跨请求的总时间预算。

## 已实施策略

| 故障类别 | 新行为 |
| --- | --- |
| 模型无可用通道 | 同一逻辑调用最多 3 次通道探测；允许短暂恢复，仍不可用则给出 `MODEL_CHANNEL_UNAVAILABLE` |
| 鉴权、订阅或权限不足 | 当次停止，提示检查凭据、权限、网关模型映射 |
| 硬额度、余额不足 | 当次停止，提示恢复额度；不与 RPM 限流混淆 |
| 请求、配置不受支持 | 当次停止，保留上游原因供修正 |
| 临时断线、过载、RPM 限流 | 保留有退避的重试、Retry-After 和最多 20 次限制 |
| 长时间无结果 | 每个逻辑文本调用的全部传输尝试共享 10 分钟预算；单次请求信号使用剩余时间，睡眠后再次检查截止时间 |

10 分钟是调用预算，不是整条工作流的预算；时间预算可能先于第 20 次耗尽。3 次探测是有意的取舍：持续路由故障尽早返回给用户，不再等待像本次第一版那样到第 12 次才可能恢复。没有宣称这种策略能恢复供应商服务。

错误正文分类同时覆盖普通 HTTP、HTTP 200 内嵌错误和 SSE 错误事件；成功生成正文不会被扫描为通道错误。SSE 的限流与普通 HTTP 限流采用相同处理。每次传输记录保留原始状态、原因分类和耗时。

停止决定通过 `retryable=false` 和明确错误类型传递到写作重试、原则审核、工作流异常回退，覆盖宽泛的 HTTP 503 重试配置，避免三层重复放大。内容质量校验与已有素材不作修改，模型配置不自动切换。

实现文件：`src/model-failure.ts`、`server/anthropic-text.ts`、`src/storyboard-runtime.ts`、`src/principle-review-runtime.ts`、`src/node-retry.ts`。运行接口 `/api/runtime-version` 新增策略版本和生效预算，便于排查“源码改了但服务未更新”。

## 容灾与恢复方案

现场核对确认 `claude-opus-4-8-doro-backup` 与主配置的 endpoint、实际 model、API 凭据均相同；它只是重复配置，不能作为独立容灾。此次未进行无意义的主备轮换，也没有将工作流悄悄切到模拟器或其他模型。

要恢复实际生成，需要供应商修正当前分组的模型路由/订阅权限，或提供真正独立且可用的模型通道。接入独立通道后，应先以小请求验证模型身份、权限和协议，再从失败节点恢复，保留已完成史料等前置输出。自动主备切换若要继续建设，应以显式允许的备用列表、独立故障域、能力兼容与记录实际路由为前提；这次没有上线自动切换，也没有可据以宣称恢复成功的独立通道。
